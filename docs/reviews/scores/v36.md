## Per criterion

### 1. Same spec, same app — 5

**Evidence.** `runs/r35-converge/report.md`: 12 apps × 3 builds × 2 targets, 72/72 builds OK and
72/72 first try, 40 sessions × 25 actions each; 11 apps 100% same app, the calculator 90% (4 of 40
sessions: elm-3 alone read a trailing "." differently), Elm≡TS 100% everywhere.
`runs/r35-calculator-fix/report.md`: after a rule and an example were added
(commit `e6cf163`), 6/6 first try, 100%. `runs/r36-screens/report.md`: the new multi-screen app,
4/4 first try, 100%, Elm≡TS 100%. `runs/history.jsonl` has the v29 round too (12 apps, 100%). Every
new spec is twin-built (build logs, e.g. `../spectavity/runs/registry-api.log`: "the probe's
reading behaves the same (24 sessions)"). The v29 "one change" (re-run converge) is done, twice.

**Biggest weakness.** Converge covers screens only. The APIs, the screens that call APIs,
stored state, effects and faults rest on single twin builds (README.md:405–477). And the
calculator ambiguity passed its twin probe and the v29 converge (100%), and only surfaced at v35:
40 sessions per app is a sample, not a proof.

**The one change.** Put the API specs and the calling screens (`apps/15`, `16`, `18`,
`apps/api/*`) in `converge`, with restarts and faults in their sessions.

### 2. Writable by an LLM — 4

**Evidence.** Part 1: two specs covering several screens, stored state, `or nothing`, data
invariants, a key layer bound to state, a job and an event reached 0/0 in two and three rounds;
every error said what to change. Several v29 complaints are fixed: impossible dates, `every 0d`,
`wait 10 days`, the false `UNMARKED` on the unit "days" (a body param `days` with "@days days
after @today" gives no hint now). Build side: 72/72 first try at v35, the new app 4/4 first try,
and the registry and hub in `../spectavity` built on the first attempt, twin-verified
(`runs/hub.log`, `runs/registry-api.log` there). `npm test` passes.

**Biggest weakness.** Holes where the checker trusts prose: `stop` accepted in an endpoint,
event body paths unchecked, `UNGUARDED` blind to record fields and to lookups ("the book whose
@id is @id") that can find nothing, the current screen not tracked in examples. Loops have no
form, so an author must invent one long sentence. Nobody but the author and this reviewer wrote a
v30+ spec: the held-out authors are from v10–v12.

**The one change.** A held-out round at v36: two or three fresh LLM authors, with stored state,
several screens and an API, measured from first check to first build.

### 3. Readable without tooling — 4

**Evidence.** `apps/19-ticket-pages.intent` reads like a site map: `screen list "/"`,
`screen ticket "/tickets/{id}"`, `go to @ticket with @id = …`, `on open ticket`. `stored` on
the state line and `effect external` / `undone by refund` on the contract
(`lib/pay/paymentsApi.intent:7–14`) say what they mean. Braces and `@` as in v29.

**Biggest weakness.** List operations are still single sentences:
`../spectavity/apps/registry-api.intent:109,146,153` ("for each @BundleName in the demand, the
chosen release is the lowest @Release … that meets the row of the demand for it with the highest
@minimum"), `apps/api/notices-api.intent:47`. And a reference can mean two things in one
phrase: `the ticket whose @id is @id` (`apps/19-ticket-pages.intent:34,38,48`; the field and the
path param), `@room = @room trimmed` in the reviewer's API.

**The one change.** List operations as forms (`for each x in @xs where … { … }`, "the @xs where
…, ordered by …"), and a way to tell a param from a field (`@path.id`, `@body.room`, or a warning
when one name is both).

### 4. Language and content apart — 4

**Evidence.** All references are marked and checked (the reviewer's `@bookz` and `@holdGone`
were errors), literals are quoted, control words are structure, and `T or nothing` replaced
stand-ins such as `0` for none (v30).

**Biggest weakness.** Every construct of v30–v36 went into the core: `or nothing`, `stored`,
`restart`, `effect external`, `undone by`, `steer`, `screen … "/path"`, `path`, `go to`, `go back`,
`on open`, `open`, `see screen`, `see path`. LANGUAGE.md grew from 1041 to 1237 lines. The profile
specs still fail `check` (`lib/profile/ui.intent`: `SYNTAX` on every `element`;
`lib/profile/api.intent` has 9 lines and none of the api words). Value choices are prose, and v36
made the prose form the recommended one: `"{…, or "No such ticket" when there is none}"`
(LANGUAGE.md §4i), `"Full" when …, otherwise …` (LANGUAGE.md:237).

**The one change.** Make profile specs a checked kind of file and move the medium words (`go
to`, `path`, `open`, `endpoint`, `every`, `steer`) into the ui and api profiles.

### 5. General — 3

**Evidence.** Time, stored state, `restart`, effects and faults work the same for screens and
services (LANGUAGE.md §3, §3b, §4f, §6). One contract (`pay.paymentsApi`) serves an API and a
screen. Several screens (v36) are addresses and history, a pattern that fits more than the web.

**Biggest weakness.** A screen spec is still a web page: the address is "the address after
`#` in the browser" (LANGUAGE.md §4i), `look` and presentations sit inside the screen, and a spec
has one medium. No terminal, no second API target (Kotlin is on the roadmap).

**The one change.** Split the look (design, presentations, `look`) of a screen from its
behaviour, so the same screen intent can be built for a second medium.

**The one change.** A small language server: go to definition for `@names`, imported names and
`go to @screen`, with diagnostics and their columns.

**The one change.** Twin-compile the invariant checks and compare them on the recorded sessions
(the same probe the apps get), and plant one bug per invariant.

## Is the language good?

**Verdict: good for small real services and multi-page tools; the first real application is
written in it.** Since v29 the language gained what a running app needs over time (stored state,
effectively-once effects, pages), and the builds stayed identical where measured. What is left is
what makes an app live through its second version: data migration, references, undo and
approval, and a checker that trusts prose less.

**Strongest points.**
1. Same spec, same app, now measured again at scale: 72/72 first try, 99% of sessions identical,
   100% across targets, and the one divergence became a spec fix.
2. The harness owns the hard, judgement-free parts: time, restarts, idempotency keys, retries,
   `unknown` answers, routing and history, with tests (`once.test.ts`, Fmt parity).
3. Examples as proofs reach new places: `restart`, `steer pay lose answer`, `open "/tickets/3"`.

**Weakest points.**
1. Behaviour over lists and lookups is still prose: no loop form, `@id` doubling as field and
   param, lookups that can find nothing go unchecked (criteria 2, 3, 9).
2. Real-app gaps that bite at the second release: stored-data migration, references, undo and
   approval (criterion 8).
3. Docs and tools for change: stale reference lines, no `fix`/`migrate`, profiles that do not
   check (criteria 4, 10, 11).

**Recommended next three changes.**
1. **Stored-data migration with identity and references** (criterion 8, and 11). A record change
   must not silently reset users' data; references remove the "whose @id is @id" lookups.
2. **List operations and lookups as forms, with a checked "none" case** (criteria 3, 2, 9).
   `for each … where … { }`, "the @x whose …" that the checker knows can be nothing, and param vs
   field made explicit.
3. **Verify the verifiers and the docs** (criteria 9, 10): twin-compile the invariant checks,
   put APIs and calling screens in `converge`, and test every doc snippet in `npm test`.

measurements in the README. No `build`, `converge` or `review` was run for this score (they

### `runs/scorecard/rooms-api.intent` (175 lines): 1 checker round

0 errors on the first run, 1 hint: `UNMARKED "end"`, reported on the `endpoint book` line (60).
The cause is the reference's own idiom "add a @Booking **to the end of** @bookings" (§5),
which collides with a field named `end`. `intent lock` was not needed.

Seven planted mistakes, to see what the checker catches: a wrong body field in `see`
(`bookr`), a misspelled `@caler`, an unknown call param (`dday`) and an unknown layer were

step was reported on the line of its block (`endpoint`, `on click`), not on the step.

## Per criterion

### 1. Same spec, same app — 4

**Evidence.**
- README.md:156–168: r5, 9 apps × 2 targets × 5 builds, 100% same app, 10/10 first-try OK for
  every app.
- README.md:288–323: four held-out specs by independent authors, 6/6 builds, 100% same app
  after two harness bugs and one language silence were fixed.
- README.md:345–353: twin compilation with a deliberately different probe; on a vague word
  counter it found three open questions that two identical compilers missed.
- README.md:377–388: screen + API, 60/60 sessions identical across Elm and TS.
- `runs/history.jsonl` has 23 rounds; the last is `v12-reanalysed`. Nothing from v13 to v26
  has a multi-build `converge` measurement; the README reports single twin builds for those.

**Biggest weakness.** Looks: held-out local layout 40–64% in round one, 56–97% in round two
(README.md:290–317). And the v24–v26 syntax changes (braces, `@`, imports) were not
re-measured with `converge`.

**The one change.** Re-run `converge` on all apps and the held-out specs at the current
version, and add them to `runs/history.jsonl`, so the claim rests on the current language.

### 2. Writable by an LLM — 4

**Evidence.** Part 1 above: 3 rounds (5 errors) and 1 round (0 errors). Four held-out authors
built 6/6 on the first try (README.md:288–317). `npm test` passes (checker regression, API
runtime, Fmt parity).

**Biggest weakness.** The docs and the checker disagree in places (LANGUAGE.md:767 vs the
checker), and the `UNMARKED` hint fires on plain English ("days", "end" in "to the end of"),
at the wrong line (`1:1` for a `rules` sentence). An LLM then rewords good prose to silence it.
SKILL.md:135 and :241 still say "write its own names in braces" (the pre-v25 form).

**The one change.** Report every diagnostic on the line of the step it is about, and make
`UNMARKED` skip words in the reference's own idioms ("the end of", "the given").

### 3. Readable without tooling — 4

**Evidence.** Every block closes with `}` (LANGUAGE.md:28–37); every reference is `@name`
(LANGUAGE.md:41–55). `apps/api/desk-api.intent` reads top to bottom: layers, seed table, one
endpoint per behaviour, examples with literal headers. A reader can tell who may do what
without the reference.

**Biggest weakness.** Dense derive sentences: `apps/07-shop.intent` `lineTotal` and the
reviewer's own `streak` are one long sentence each; a reader cannot tell the exact rule
without an example. Built-in behaviour (typing sets state, a checkbox flips a field) is
invisible in the spec.

**The one change.** The small structured grammar for behaviour (language review #1):
"A when C, otherwise B", list operations and early exits as forms, English only in the leaves.

### 4. Language and content apart — 3

**Evidence.** Good: `@` on references, quoted literals, profiles as specs
(`lib/profile/ui.intent`, `lib/profile/api.intent`). Weak: the core has about 40 keyword
forms (app, bundle, contract, layer, profile, import, use, uses, implements, extends,
override, add to, drop, record, choice, type, design, component, state, clock, derive, screen,
on, rules, always, example, endpoint, event, publish, param, provides, before every request,
after every answer, before every call, examples with, given, tested with, through, every
endpoint answers …). The presentation table (LANGUAGE.md:211–248) is in the reference, not a
profile. The profile specs themselves do not pass the checker (`check lib/profile/ui.intent`:
`SYNTAX: unknown block element`).

**Biggest weakness.** Semantic idioms are unmarked prose: "and stop", "otherwise", "that
<item>", "its", "the given" (LANGUAGE.md:706–719). A reader cannot tell which words the
compiler treats as language.

**The one change.** Same as #3: make the handler idioms parsed forms, so language words are
keywords and the rest is content.

### 5. General — 3

**Evidence.** `support.tickets` serves a screen (`apps/15-tickets-ui.intent`) and two APIs;
layers are medium-free specs. But a screen spec names web layout: `as sidebar`, `as drawer`,
`as toast`, `look "…"`. One screen per app (README.md:453). There is no second target medium
for screens (terminal) and no second language target for APIs (Kotlin is on the roadmap).

**Biggest weakness.** Intent and medium are mixed inside a screen spec.

**The one change.** Split a screen spec's look (presentations, `look`, `design`) into a
separate layer or profile file, so the same screen intent can get another medium.

### 6. Traceable — 3

**Evidence.** Good: `data-el` names and `sourcemap.json` for screens
(`runs/single/12-helpdesk-bundled/elm/sourcemap.json`, element → file:line, with component
and bundle); v26 makes every name's origin visible in the file. Weak:
`runs/single/desk-api/ts/sourcemap.json` (built today) holds only two `state` entries; no
endpoint, step, layer or answer. `compiler/load.ts:519–542` confirms that `sourceMap` walks
only the screen, state, derive and handlers. No go-to-definition or language server
(`compiler/` has none). Checker errors point at the block, not the step (Part 1).

**Biggest weakness.** An API answer cannot be traced to the endpoint step or layer that made
it, which is exactly the API half of the vision in `AGENTS.md`.

**The one change.** Put endpoints, their steps, layers and events in the source map, and tag
each answer in tests with the step that produced it.

### 7. Reuse and composition — 4

**Evidence.** Bundles with demos (`lib/std/list.demo.intent` and others), behaviour
components, three HTTP layers compiled once and copied in (README.md:399–404), contracts
checked in three places (LANGUAGE.md:518–537), refinement with proofs that still run
(README.md:325–341), `intent.lock`, a registry with minimal version selection and computed
versions (LANGUAGE.md:403–432).

**Biggest weakness.** The library is small (std.list, std.feedback, std.text, ui.admin,
support.*, three http layers, one client layer), all imports share one flat namespace
(LANGUAGE.md:263), refinement is one level deep, and bundle components cannot be restyled.

**The one change.** Namespaced imports (`list.Pager`), so libraries from different authors
can be combined without clashes.

### 8. Covers real apps — 3

**Evidence.** `docs/reviews/openouros.md` §3: time is in 20 of 38 contracts, effects about
50%, persistence about 85% of features, unions about 35%. Of these, only events (v22) and
keys (v21, v23) are done. The planned v23 (time) and v24 (effects) in `AGENTS.md` became
syntax work instead. The reviewer's habit tracker had to fake the date with a counter and a
"Next day" button; the booking API had to use day numbers and whole hours.

**Biggest weakness.** No time, no stored state, no effects, one screen per app.

**The one change.** Time: a date/time type and a steerable clock in screens and APIs, with
`clock at …` in examples.

### 9. Verifiable — 4

**Evidence.** A planted rounding bug that passed every example was caught in 20 of 40
sessions (README.md:151–152); eight planted layer bugs were each caught (README.md:407–408);
the measurement itself was audited and two harness bugs fixed (README.md:293–297); per-row
numeric `always` (LANGUAGE.md:755–768); contract checks on every answer.

**Biggest weakness.** Invariants across rows and over state not on screen are not checkable.
The workaround puts a fake alert on the screen (LANGUAGE.md:770–772), as in the reviewer's
habits spec. `rules` sentences are never checked, and there is no warning for that. The
checker lets `see x.body.n = "ten"` through for an `Int` field.

**The one change.** A small closed form for model-level invariants (each / unique / count /
sum over state), plus a warning for every `rules` sentence no check covers.

### 10. Consistent — 3

**Evidence.** Uniform now: braces, `@`. Still several forms:
- template holes: `{count}`, `{@subtotal as money}` (`apps/07-shop.intent:66`),
  `{number of @items not @done}` (GUIDE.md:145), and the same template without `@` in the
  guide's own text (GUIDE.md:180);
- `use` places a component and also a layer; `uses` names a contract;
- `app Name { "purpose" }` (LANGUAGE.md:67) next to a bare `app TicketsApi` (LANGUAGE.md:441);
- stale examples: the `design` / `component` snippet in the indentation form
  (LANGUAGE.md:191–205), the Pager in the v10 `{items}` form (README.md:238–251), "in
  braces" in SKILL.md:135 and :241.

**Biggest weakness.** The docs, which an LLM copies, show old forms next to new ones.

**The one change.** Make every snippet in the docs pass `check` and `fmt --check` in `npm test`.

### 11. Evolvable — 3

**Evidence.** Wishes are local: an example, an `always` line, an override (`apps/14-supportdesk.intent`).
The lock pins the language and model and warns when they change (`compiler/load.ts:98–103`).
But `grep "language v"` over `apps/` and `lib/` finds 0 specs that pin a version. `intent fmt`
only rewrites indentation to braces (`compiler/cli.ts:92–104`); a file with a 6-space indent
passes `fmt --check`; there is no migration for v25 (`@`) or v26 (imports); `fmt` is missing
from the CLI's usage text. Stability across spec edits is **not measured** (README.md:461).

**Biggest weakness.** Language changes are migrated by hand.

**The one change.** `intent migrate` per version (at least `@`-marking and import insertion),
and a `language vN` line written by `fmt` into every spec.

## Is the language good?

**Verdict: yes for single-screen tools and small CRUD APIs; not yet for real applications.**
For what it covers, a spec gives the same app every time and a vague spec is caught, which is
rare and well measured. It cannot yet describe time, stored data, effects or several screens,
so a real product would have to be faked around it.

**Strongest points.**
1. Same spec, same app, measured: 100% agreement across targets and independent authors, and
   a twin probe that turns ambiguity into a question with a line number.
2. The harness owns what needs no judgement: routing, validation, rounding, CORS, keys. The
   layers and contracts are verified once and reused.
3. Easy to write: one of two new specs checked on the first run, the other in three.

**Weakest points.**
1. Real-app coverage: no time, persistence, effects or navigation (openouros gaps G2, G3, G5,
   G6).
2. API traceability: answers and endpoint steps are not in the source map, and checker
   diagnostics point at blocks, not steps.
3. Behaviour is free English with semantic idioms hidden in it; the most important rules
   (across rows) are unchecked prose or need a fake screen element.

**Recommended next three changes.**
1. **Time and a steerable clock** (criterion 8, weight 10, score 3). It unblocks the largest
   share of openouros and removes the fakes in both reviewer specs.
2. **API traceability and step-level diagnostics** (criterion 6, weight 10, score 3; also
   criterion 2). Small work, and it closes the API half of the traceability requirement.
3. **Model-level invariants with a `rules` coverage warning** (criterion 9, weight 8, and
   criterion 8). It removes the fake-alert workaround and prepares the ground for stored state
   ("never booked twice" is the first thing a store needs).

The structured grammar for behaviour (criteria 3, 4, 10) is the next after these: it raises
three scores, but by less per unit of weight than the three above.

## Per criterion

### 1. Same spec, same app — 4

**Evidence.** README.md:156–168 (r5: 9 apps × 2 targets × 5 builds, 100% same app);
README.md:288–323 (four held-out specs, 100% after fixes); README.md:382–393 (screen + API,
60/60 sessions Elm≡TS); README.md:403–409 (v28: habits 60/60 Elm≡TS with 286 waits; notices API
twin-verified); README.md:396–401 (v29: todo, shop, pomodoro, library, both API screens with their APIs and layers, and the notices API rebuilt on the first attempt, twin-verified).
The harness owns the clock in tests (LANGUAGE.md §3b, §9.8), so time adds no randomness.
`runs/history.jsonl` has 23 rounds; the last is `v12-reanalysed`.

**Biggest weakness.** No multi-build `converge` since v12. Everything from v13 to v29 (braces,
`@`, imports, time, structure) rests on single twin builds.

**The one change.** Re-run `converge` over all apps, the API specs and the held-out specs at
v29, and log it in `runs/history.jsonl`.

### 2. Writable by an LLM — 4

**Evidence.** Part 1: two specs covering time, `wait`, events, a recurring job, structured
`if / else if / answer / stop` and the key layer checked with 0 errors on the first run, and 0
hints on the second. The error messages for real mistakes are precise and mostly say how to
fix them. `npm test` passes (checker regression, API runtime, Fmt parity).

**Biggest weakness.** The checker is lenient where it matters: behaviour is prose, so the
date phrasing an author invents ("plus N days", "the number of days from … to …") is never
checked before a build, and impossible dates pass. At the same time `UNMARKED` fires on the
English unit "days", which pushed the reviewer to rename a wire field. The skill still teaches
`answer 404 … and stop` (SKILL.md:196–197), which v29 marks as `UNSTRUCTURED`.

**The one change.** A closed list of date phrases (like the rounding words in §9.9), checked
by the checker, with `UNMARKED` skipping unit words after a number or reference.

### 3. Readable without tooling — 4

**Evidence.** `runs/scorecard-v29/library-api.intent` `lend`: the refusal order is visible as
one `if … else if … else if` chain, and each `answer` is visibly the end. Blocks close with `}`,
references are `@name`, seed data is a table, layers read as configuration.

**Biggest weakness.** Whole behaviours are one sentence: the `every 1m` step in
`apps/api/notices-api.intent:47` (filter, remove, order, publish for each) and the habits streak
(`apps/17-habits.intent:40`). A reader cannot tell the exact rule without the examples.

**The one change.** List operations as forms (`for each … in @x where … { }`, "the @x where …,
ordered by …"), with English only in the conditions.

### 4. Language and content apart — 4

**Evidence.** v29 made `if`, `else if`, `else`, `answer`, `stop` parsed structure
(LANGUAGE.md:754–775), with `UNSTRUCTURED` for prose control. References are marked, literals
quoted, and the UI and API vocabularies are profile specs (`lib/profile/ui.intent`,
`lib/profile/api.intent`).

**Biggest weakness.** The core keeps growing (time literals, `every`, `examples start at`,
`wait`, `publish`, layers, contracts, refinement all live in LANGUAGE.md, 1041 lines). The
profile specs do not pass `check` (`lib/profile/ui.intent`: 12 `SYNTAX` errors). Value-level
choices are still prose: `text places = "Full" when …, otherwise …` (LANGUAGE.md:212).

**The one change.** Make the profile specs a checked kind of file, and move the api words
(`endpoint`, `answers`, `request`, `every`) into the api profile the same way the UI words are.

### 5. General — 3

**Evidence.** Time (`Date`, `@today`, `wait`) works in screens and APIs alike; one domain bundle
serves a screen and two APIs (`support.tickets`); layers are medium-free. But a screen spec
names web layout (`as sidebar`, `as drawer`, `look "…"`), there is one screen per app
(README.md:474), and no terminal or second API target (openouros G6).

**Biggest weakness.** Intent and medium are mixed inside a screen spec.

**The one change.** Split the look (design, presentations, `look`) of a screen into its own
file or profile, so the same screen intent can be built for another medium.

### 6. Traceable — 4

**Evidence.** `runs/single/notices-api/ts/sourcemap.json` maps `endpoint post`, each of its
steps (`step 1` → line 28, `if @text, trimmed, is blank {`), the event and every example to file
and line. `compiler/api.ts:227` adds `x-intent-source` under `INTENT_TRACE=1`. Checker errors
now name the step's own line (Part 1: `UNREACHABLE` at the step). `data-el` for screens. v26's
import rule makes every name's origin visible in plain text.

**Biggest weakness.** No go-to-definition or language server (nothing in `compiler/`). The
`every` job is not in the source map (no `every` key in the notices map). Diagnostics always
report column 1. Pointing at an element in the running app, and a bug report that becomes a
failing example, are still missing (AGENTS.md).

**The one change.** A small language server: go to definition for `@names` and imported names,
and diagnostics with columns.

### 7. Reuse and composition — 4

**Evidence.** Bundles with demos, behaviour components, layers compiled once and copied in
(README.md:420–425), contracts checked in three places (LANGUAGE.md §4f), refinement with the
base's proofs (`apps/14-supportdesk.intent`), `intent.lock` pinning bundles, the language and
the model, a registry with minimal version selection and computed versions (LANGUAGE.md §4d).
The library-api spec got auth by binding a table (Part 1).

**Biggest weakness.** The library is small (`std.list`, `std.feedback`, `std.text`,
`ui.admin`, `support.*`, four http layers); there is no `std.time`; all imports share one flat
namespace (LANGUAGE.md:294); refinement is one level; bundle components cannot be restyled.

**The one change.** Namespaced imports, so bundles from different authors can be combined.

### 8. Covers real apps — 3

**Evidence.** v28 closes openouros G2 (time and a clock in APIs) and part of the background
work: the reviewer's plants and library specs needed no fake day counter, unlike the v26
reviewer's habits spec. Events (v22) and keys (v21, v23) were already there. Still missing
(docs/reviews/openouros.md §3): stored state and restart (about 85% of features persist),
effects with approval, outbox and compensation (about 50%), unions of records and wire names
(about 35%), several screens and navigation (README.md:474).

**Biggest weakness.** No stored state and no effects: a real app's data and side effects are
in-memory fakes.

**The one change.** Effects on actions (approval, permissions, outbox, compensation), which the
roadmap already names as v24 (AGENTS.md §7), then stored state.

### 9. Verifiable — 4

**Evidence.** A planted rounding bug caught in 20 of 40 sessions (README.md:151–152); eight
planted layer bugs each caught (README.md:428–429); the twin probe found a real CORS gap
(README.md:430–433); the Fmt parity test covers dates, leap years and dates before 1970
(`npm test`); random sessions mix in waits (LANGUAGE.md §3b); contracts check every answer; v27
checks `see x.body… = value` against the field's type (Part 1: "tomorrow" for a Date is caught).

**Biggest weakness.** Invariants over state, across rows or over time cannot be checked: the
plants rule "never watered twice on one day" stays an unchecked `rules` sentence, and nothing
warns about it. The checker accepts `2026-02-30`, `2026-13-40` and `every 0d`.

**The one change.** A small closed form for model-level invariants (each / unique / count over
state), plus a warning for every `rules` sentence that no check covers.

### 10. Consistent — 3

**Evidence.** v29 gives one form for choices in handlers, endpoints and layers. But:
- recurring time has two forms: `clock every 1s` + `on tick` in screens, `every 1m { … }` in
  APIs (LANGUAGE.md:79, :147);
- an inline endpoint says `returns T`, a contract says `answers 201 T` (§4e vs §4f);
- a layer's examples say `see status`, an api's say `see x.status`;
- a value choice is still prose ("…, otherwise …"), a step choice is structure;
- the docs contradict v29: LANGUAGE.md:750 "Sentences may be conditional ('if draft is blank,
  do nothing')", SKILL.md:196–197 "answer 404 … and stop"; LANGUAGE.md:62 lists durations
  without `h` and `d`; README.md:72 says 16 screens and 2 APIs (there are 17 and 3).

**Biggest weakness.** The docs an LLM copies still show forms that the checker now flags.

**The one change.** Test every snippet in GUIDE, LANGUAGE and SKILL with `check` and
`fmt --check` in `npm test` (today only the presentation table is tested, `tests/checker/run.ts:31–36`).

### 11. Evolvable — 3

**Evidence.** Wishes stay local: the plants "once a day" rule was one `enabled when`, one `if`
and one example. The lock pins the language (`intent.lock`: `@language v29 sha256:…`), and
`language vN` gives a `LANGUAGE` warning. But v29 broke `runs/openouros/03-yoga-booking.intent`
(pinned `language v21`): 6 `NO_ANSWER` errors, no migration offered. `fmt` only moves
indentation to braces, and it is still missing from the CLI usage text. Only the three
openouros slices pin a version; no spec in `apps/` or `lib/` does. Stability across spec edits
is **not measured** (README.md:482).

**Biggest weakness.** Every language change is migrated by hand.

**The one change.** `intent migrate`: at least prose "and stop" / "otherwise" → structure,
`@`-marking and import insertion, driven by the `language vN` line, which `fmt` writes.

## Is the language good?

**Verdict: good for single-screen tools and small APIs with time, events and keys; not yet for
real applications.** A fresh author can now write a time-dependent screen and a key-protected
API with a daily job that pass the checker on the first run, and the harness keeps builds
identical. Stored state, effects and several screens are still missing, and the checker trusts
prose where exactness matters most (dates, invariants).

**Strongest points.**
1. Same spec, same app, measured and enforced: 100% agreement where measured, and a twin probe
   on every new spec that turns ambiguity into a question with a line.
2. Easy to write correctly: both reviewer specs checked on the first run, and the checker's
   messages for real mistakes (`NO_ANSWER`, `UNREACHABLE`, unknown fields, layer params) say how
   to fix them.
3. The harness owns what needs no judgement, now including time: a steerable clock, date
   helpers with a parity test, layers and contracts verified once.

**Weakest points.**
1. Real-app coverage: no stored state, effects or navigation (criterion 8).
2. Invariants beyond one screen row cannot be checked, and nothing warns about unchecked
   `rules` sentences (criterion 9).
3. Evolution and docs: language changes break old specs with no migration, and the docs still
   teach forms the checker flags (criteria 10, 11).

**Recommended next three changes.**
1. **Effects, then stored state** (criterion 8, weight 10, score 3). It is the largest remaining
   gap in openouros and the next item on the roadmap.
2. **Model-level invariants with a `rules` coverage warning** (criterion 9, weight 8, and
   criterion 8). Stored state needs "never booked twice" as a real check, and the plants spec
   shows the same need at small scale.
3. **Docs under test plus `intent migrate`** (criteria 10 and 11, weight 5 each, and criterion 2).
   Cheap, and it stops LLM authors from copying forms the checker rejects.

A `converge` run at v29 (criterion 1) should come before any of these: it costs money, but the
highest-weighted claim rests on a v12 measurement.
